## 1. User Flows

### UF-01 — Реєстрація нового користувача

| Поле               | Опис                                                                 |
|--------------------|----------------------------------------------------------------------|
| **Актор**          | Анонімний відвідувач                                                 |
| **Мета**           | Створити акаунт у системі TaskBoard                                  |
| **Передумова**     | Сервер запущений; акаунту з цим email не існує                       |
| **Крок 1**         | Перейти на `/register`                                               |
| **Крок 2**         | Ввести ім'я, валідний email та пароль (≥8 символів, ≥1 цифра)       |
| **Крок 3**         | Натиснути "Зареєструватись"                                          |
| **Очікуваний результат** | Акаунт створено; редирект на `/profile`                        |
| **Альтернативний шлях**  | Email вже існує → 409 + повідомлення про дублікат              |
|                    | Слабкий пароль → 400 + повідомлення з вимогами                       |

### UF-02 — Авторизація та блокування після 5 невдалих спроб

| Поле               | Опис                                                                 |
|--------------------|----------------------------------------------------------------------|
| **Актор**          | Зареєстрований користувач                                            |
| **Мета**           | Увійти до особистого акаунту                                         |
| **Передумова**     | Акаунт існує; акаунт не заблокований                                 |
| **Крок 1**         | Перейти на `/login`                                                  |
| **Крок 2**         | Ввести email і пароль                                                |
| **Крок 3**         | Натиснути "Увійти"                                                   |
| **Очікуваний результат** | Вхід успішний; редирект на `/profile`                          |
| **Альтернативний шлях**  | Невірний пароль → 401 + повідомлення + лічильник               |
|                    | 5-та невдала спроба → 403 + "Акаунт заблоковано"                     |


### UF-03 — Оновлення профілю та захист після виходу

| Поле               | Опис                                                                 |
|--------------------|----------------------------------------------------------------------|
| **Актор**          | Авторизований користувач                                             |
| **Мета**           | Змінити ім'я в профілі та безпечно завершити сесію                   |
| **Передумова**     | Користувач авторизований                                             |
| **Крок 1**         | Перейти на `/profile`                                                |
| **Крок 2**         | Ввести нове ім'я та натиснути "Зберегти"                             |
| **Крок 3**         | Натиснути "Вихід"                                                    |
| **Крок 4**         | Спробувати відкрити `/profile` без авторизації                       |
| **Очікуваний результат** | Ім'я оновлено; після виходу `/profile` → редирект на `/login` |
| **Альтернативний шлях**  | Порожнє ім'я → 400 + "Ім'я не може бути порожнім"             |



## 2. Acceptance Criteria (Gherkin)

### Feature: Реєстрація нового користувача (UF-01)

```gherkin
Scenario AC-01: Happy path — успішна реєстрація
  Given сервер TaskBoard запущений і база порожня
  And користувач перейшов на /api/register
  When користувач надсилає ім'я "Олексій", email "alex@test.com", пароль "secret123"
  Then сервер повертає статус 201
  And відповідь містить поле "message" зі значенням "Реєстрація успішна"
  And email "alex@test.com" з'являється в базі користувачів

Scenario AC-02: Дублікат email
  Given в базі вже існує акаунт "alex@test.com"
  When надсилається запит на реєстрацію з тим самим email
  Then сервер повертає статус 409
  And відповідь містить "Email вже зареєстрований"

Scenario AC-03: Слабкий пароль
  Given сервер запущений
  When надсилається реєстрація з паролем "abc" (менше 8 символів)
  Then сервер повертає статус 400
  And відповідь містить повідомлення про вимоги до пароля
```

### Feature: Авторизація та блокування (UF-02)

```gherkin
Scenario AC-04: Happy path — успішний вхід
  Given акаунт "bob@test.com" існує з паролем "pass2026"
  When надсилається запит /api/login з правильними даними
  Then сервер повертає статус 200
  And відповідь містить "Вхід успішний"
  And відповідь містить ім'я користувача

Scenario AC-05: Невірний пароль
  Given акаунт "bob@test.com" існує
  When надсилається запит з невірним паролем "wrongpass1"
  Then сервер повертає статус 401
  And відповідь містить "Невірний email або пароль"

Scenario AC-06: Блокування після 5 невдалих спроб
  Given акаунт "bob@test.com" існує
  When надсилається 5 запитів з невірним паролем поспіль
  Then на 5-ту спробу сервер повертає статус 403
  And відповідь містить "Акаунт заблоковано"
```

### Feature: Оновлення профілю та вихід (UF-03)

```gherkin
Scenario AC-07: Happy path — оновлення імені
  Given акаунт "carol@test.com" існує в базі
  When надсилається запит /api/profile з новим ім'ям "Кароліна"
  Then сервер повертає статус 200
  And відповідь містить "Профіль оновлено"
  And поле "name" у відповіді дорівнює "Кароліна"

Scenario AC-08: Порожнє ім'я при оновленні
  Given акаунт "carol@test.com" існує в базі
  When надсилається запит /api/profile з порожнім рядком як ім'ям
  Then сервер повертає статус 400
  And відповідь містить "Ім'я не може бути порожнім"

Scenario AC-09: Захист /profile після виходу
  Given сервер запущений
  When неавторизований клієнт надсилає GET /profile
  Then сервер повертає редирект (302) на /login
```

## 6. Release Recommendation

###  READY FOR RELEASE

**Обґрунтування:**

Усі три критичних user flow пройшли валідацію повністю:

- **UF-01 (Реєстрація):** система коректно створює акаунти з валідними даними, блокує дублікати та відхиляє слабкі паролі.
- **UF-02 (Авторизація):** вхід працює з правильними даними; після 5 невдалих спроб акаунт блокується і залишається заблокованим навіть з правильним паролем — захист від brute force реалізовано коректно.
- **UF-03 (Профіль/Вихід):** оновлення імені зберігається; порожнє ім'я відхиляється; `/profile` без авторизації перенаправляє на `/login` — сесійний захист працює.

Жодного FAIL або BLOCKED сценарію не зафіксовано. Система відповідає всім сформульованим acceptance criteria.
